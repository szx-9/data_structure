# 检索系统设计大纲——从问题拆解到数据结构选型

> 核心问题：给你一篇文档和一个查询句，找出文档中与查询最相关的 K 个句子。
> 技术手段：把句子变成向量，用余弦相似度衡量"相关程度"。

---

## 一、先用自然语言理解这个系统

### 1.1 它在做什么？

这个系统做的事情用一句话概括：

> 把文档拆成句子 → 把句子变成向量 → 用户提问时，找到向量最接近的那几句。

但这句话背后藏了很多细节。我们把整个过程拆成**两个阶段**：

| 阶段 | 做什么 | 什么时候做 | 对速度的要求 |
|------|--------|------------|:---:|
| **入库**（建索引） | 读文档、分词、建词典、算向量，把一切准备好 | 文档加载时（一次性） | 可容忍较慢，但内存要省 |
| **查询**（检索） | 用户输入 query → 算向量 → 和所有句子比相似度 → 返回 Top-K | 每次用户提问时 | **必须快** |

### 1.2 先做哪个？

从开发顺序上看，**肯定是先入库、再查询**——没有索引你查什么？所以开发节奏是：

```
第一步：把入库流程跑通（读到文档 → 分句 → 分词 → 建词典 → 存句子 → 算向量）
第二步：把查询流程跑通（读 query → 分词 → 查词典 → 算向量 → 算相似度 → 输出 Top-K）
第三步：验证样例、调优、考虑大规模
```

我们按这个顺序来拆。

---

## 二、功能需求逐层拆解 → 引出数据结构

每一步，我们都问三个问题：
1. **要干什么？**（功能需求）
2. **需要什么操作？**（抽象操作）
3. **什么数据结构最适合？**（具体选型 + 为什么）

---

### 2.1 功能一：分句

**要干什么**：把一整篇文档按 `.` `?` `!` `\n` 切成独立的句子。

**需要什么操作**：扫描字符，遇到分隔符就切一刀。保留分隔符在句尾（题目要求）。

**需要什么数据结构**：这一层**不需要特殊数据结构**。用 `strtok` 或手动遍历字符串即可。切出来的句子存成字符串数组。

**注意**：不要把分隔符丢掉。`strtok` 会吃掉分隔符，所以要么自己写扫描逻辑，要么用 `strtok` 后手动补回分隔符。

---

### 2.2 功能二：分词 + 清洗 + 去停用词

**要干什么**：
- 把每句话按空白符和标点切成单词（但 `'` 不分，保留 `don't`）
- 全部转小写
- 过滤掉停用词

**需要什么操作**：

这里最核心的操作是「判断一个词是不是停用词」。停用词表有 **891 个词**，按字典序排列，每行一个。如果每遇到一个词都线性扫描 891 个词的列表……

```
最坏情况：891 次 strcmp × 每句 ~20 词 × 10000 句 = 1.78 亿次字符串比较
```

这在百万级文档上是**不可接受的**。

**数据结构选型：有序数组 + 二分查找**

停用词表天然有序（题目保证了），那就用二分查找：

| 方案 | 查找复杂度 | 插入 | 适合吗 |
|------|:---:|:---:|:---:|
| 无序数组 + 线性扫描 | O(N) | O(1) | 太慢 |
| **有序数组 + 二分查找** | **O(log N)** | — | **完美：只查不插，数据天然有序** |
| 哈希表 | O(1) | O(1) | 也行，但要额外建表 |
| 平衡树 | O(log N) | O(log N) | 杀鸡用牛刀 |

**选二分查找的理由**：
- 停用词文件本身就有序 → 读进来就是有序数组，零额外预处理
- `log₂(891) ≈ 10`，每次判断只需 10 次字符串比较
- `bsearch()` 是 C 标准库函数，一行代码搞定
- 停用词表是**只读的、固定不变的**——完美匹配有序数组

**结论**：停用词用 `bsearch()` 或手写二分，无需任何动态数据结构。

---

### 2.3 功能三：构建全局词典（词 → 编号）

**要干什么**：

遍历文档中所有清洗后的有效词，给每个**首次出现**的不同单词分配递增编号（0, 1, 2, …）。之后每个词都用一个整数代表，这就是「语义向量」的维度索引。

**需要什么操作**：

| 操作 | 频率 | 说明 |
|------|:---:|------|
| **插入**（新词） | 每个唯一词 1 次 | 第一次遇到某词时，分配新编号，记下来 |
| **查找**（已有词） | 文档中每个词 1 次 | 再次遇到某词时，查出它已有的编号 |
| **反查**（编号→词） | 调试时用 | 给定编号 7，知道它对应 "generation" |

注意：**不涉及删除**。词典一旦建好，只有查和增。

**核心矛盾**：既要根据「字符串」找到「编号」（正向查找），又要根据「编号」找到「字符串」（反向查找）。

**反向查找超级简单**：用一个数组 `word_by_index[i]` 存第 i 个词的指针，O(1)。

**正向查找才是难点**：文档中可能有几万到几十万个不同词，每次遇到一个词都要查「这个词有没有见过？编号是多少？」。如果用数组顺序扫 → O(N_dict)，十万个词就要扫十万次，不可接受。

---

#### 2.3.1 正向查找的解决方案：哈希表

我们要的是一个 **key→value 映射**，key 是字符串，value 是编号。需要 O(1) 的查找。

两个主流方案：

| | 开放寻址法 (Open Addressing) | 链地址法 (Separate Chaining) |
|------|------|------|
| **结构** | 所有条目放在一个大数组里，冲突时找下一个空位 | 每个槽挂一个链表，冲突时追加到链表 |
| **内存** | 一块连续数组，cache 友好 | 数组 + N 个链表节点，分散在堆各处 |
| **指针追逐** | 无（只有数组下标跳转） | 有（沿链表 next 指针走） |
| **删除** | 需要惰性删除（tombstone），较麻烦 | 直接从链表摘除，简单 |
| **负载因子** | 必须 < 0.7，否则性能急剧恶化 | 可到 1.0 甚至更高 |
| **最坏情况** | 连续冲突 → O(N)（但好的哈希函数 + 低负载可避免） | 所有 key 哈希到同一个槽 → O(N) |

**对本场景的分析**：

- ✅ 无删除需求 → 开放寻址的 tombstone 问题不存在
- ✅ 数据集中加载（入库时一次性插入），之后只有查询 → 负载因子可控
- ✅ 内存连续 → CPU cache 友好，对大规模数据尤为重要
- ✅ value 是整数，可以和后继指针合并存储（节省空间）

**我们选开放寻址法。**

---

#### 2.3.2 开放寻址的核心问题：冲突了怎么办？

开放寻址的槽位有三种状态：**空**（从未使用）、**占用**（存了一个 key-value）、**墓碑**（曾占用但被删了——不过我们不删，所以只要前两种）。

冲突解决——当 `hash(key)` 指向的槽已被占用时，找下一个槽。三种经典策略：

**（1）线性探查 (Linear Probing)**

```
index = (hash(key) + i) % table_size    // i = 0, 1, 2, 3, ...
```

- 从冲突点开始，一个一个往后找
- 实现最简单
- **主聚类问题**：一旦形成连续占用区，新插入容易"粘"上去，聚类越来越大，查找越来越慢

**（2）二次探查 (Quadratic Probing)**

```
index = (hash(key) + c1*i + c2*i²) % table_size
```

- 跨步越来越大，减少主聚类
- **次级聚类**：相同 hash 值的 key 探查路径完全一样，仍会聚类
- 需要 table_size 是质数且负载因子保持较低，否则可能探查不到空位

**（3）双重哈希 (Double Hashing)**

```
index = (hash1(key) + i * hash2(key)) % table_size
```

- 不同 key 用不同的步长，几乎消除聚类
- 需要两个哈希函数，且 `hash2(key)` 不能为 0
- 分布最均匀，但计算成本略高

**（4）Robin Hood 哈希（线性探查的增强版）**

线性探查 + 一条额外规则：**插入时，如果当前 key 的"探查距离"大于槽中已有 key 的探查距离，就把它挤走（swap），自己坐进去**。

```
探查距离 = 当前位置 - hash(key)（模 table_size）
```

效果：所有 key 的探查距离趋于平均，最坏探查长度显著降低，查询稳定。

---

#### 2.3.3 我们的选择

| 维度 | 评估 |
|------|------|
| **实现复杂度** | 这是课程项目，线性探查足够；Robin Hood 是锦上添花 |
| **性能** | 几十万个词 + 低负载因子 → 线性探查的聚类不是大问题 |
| **稳定性** | 我们的 key 是 StringPool 指针，哈希值可预计算并缓存 |

**推荐方案**：**线性探查**，搭配以下保障：
- 初始表大小取**大于 N_dict 的质数**（或 2 的幂 + 位掩码取模）
- 负载因子超过 0.6~0.7 时，**扩容 2 倍 + rehash**
- 扩容时因为 key 是 StringPool 指针（地址不变），只需重算哈希值，不涉及字符串拷贝

如果后续性能测试发现探查链过长，再升级为 Robin Hood。

---

#### 2.3.4 哈希函数的选择

由于 key 是 StringPool 指针，有两条路：

| 方案 | 做法 | 优缺点 |
|------|------|------|
| 对指针指向的字符串哈希 | `hash(ptr)` 读取 `*ptr` 指向的字符串内容 | 语义正确，每次查找需读内存 |
| 预计算 + 缓存 | 在 StringPool intern 时计算 hash，存到某处 | 查找时直接比较 hash，快 |

**推荐**：预计算哈希值，存在 StringPool 的元数据中（或独立数组）。因为每个词只 intern 一次，哈希也只算一次。查找时先比较 hash 值，hash 相同再 `strcmp` 确认（防止哈希碰撞）。

---

### 2.4 功能四：存储语句及其向量

**要干什么**：每条语句需要一个记录，包含：

| 信息 | 用途 |
|------|------|
| 原始文本 | 最终输出时需要原句 |
| 有效词列表 | 语义向量的原材料 |
| 7 维结构向量 | 结构相似度计算 |
| L2 范数 | 余弦相似度的分母（预计算，避免每次查询重复算） |

**关键决策：语义向量怎么存？**

语义向量的维度 = 全局词典大小（N_dict）。如果文档有 10 万个不同词，每条句子的向量就有 10 万维。但一条句子通常只有 5-30 个有效词——99.9% 以上的维度是 0。

| 存储方式 | 每条句子占用 | N_dict=10 万时 |
|------|:---:|:---:|
| 稠密数组 `float[N_dict]` | N_dict × 4 字节 | 400 KB |
| 稀疏 `(index, count)` 对 | 实际词数 × 8 字节 | ~200 字节 |

别说 1 万条句子，**1000 条稠密向量就吃掉 400 MB**，而且还慢（点积时要遍历 10 万个零）。

**选稀疏存储**：每条句子存一个 `(word_index, tf_count)` 的排序列表，按 word_index 升序排列。

**为什么排序？** 计算点积时，query 的稀疏向量和句子的稀疏向量可以**双指针归并**，O(N_q + N_s) 时间内完成，类似于归并排序的 merge 过程。

---

### 2.5 功能五：Top-K 选择

**要干什么**：从 N 条句子的相似度分数中，选出最高的 K 条。K 通常很小（如 3、10）。N 可能很大（十万、百万）。

**方案对比**：

| 方案 | 时间 | 空间 | 适合吗 |
|------|:---:|:---:|:---:|
| 全排序 (`qsort`) | O(N log N) | O(N) | 太慢，且不需要全排序 |
| **小顶堆** | **O(N log K)** | **O(K)** | **完美：K 很小** |
| 快速选择 (QuickSelect) | O(N) 平均 | O(N) | 也行，但不如堆直观 |

**小顶堆的工作方式**：
1. 维护一个大小为 K 的最小堆（堆顶是堆中最小值）
2. 遍历每条句子的得分：
   - 堆未满 → 直接插入
   - 堆已满 → 如果得分 > 堆顶，弹出堆顶并插入新得分；否则跳过
3. 遍历结束后，堆中的 K 个元素就是 Top-K
4. 依次弹出（得到升序），反转即得降序

**Tie-breaking**：得分相同时，按 `sentence_id` 升序排列（题目要求"先出现先输出"）。在堆比较函数中: `if (score_a != score_b) return score_a - score_b; else return sentence_id_b - sentence_id_a;`（小顶堆用反向比较保持较小 sentence_id 在顶部）。

---

### 2.6 阶段小结：数据结构全景

回顾刚才的推导路径：

```
分句 → 只需字符串数组，无特殊数据结构
  ↓
去停用词 → 有序数组 + 二分查找（表天然有序、只读、不大）
  ↓
全局词典 → 开放寻址哈希表（key=词指针, value=递增编号）
           + 索引数组 word_by_index[]（编号→词指针的反查）
  ↓
语句存储 → 稀疏 TF 列表（每句存 (word_index, count) 排序对）
         + float[7] 结构向量原始值
         + float L2 范数（预计算）
  ↓
Top-K → 大小为 K 的小顶堆
```

## 三、内存管理的基石：StringPool

### 3.1 为什么不能每个词 malloc 一次？

假设文档有 5 万个唯一词，加上每个句子持有的原始文本指针：

```
传统方式：5万次 malloc("word") → 堆中散布 5 万个小块
问题：
  1. 每个 malloc 块有 8~16 字节的元数据（记录块大小、标志位等）
     → 5万次 × 16字节 = 800KB 纯浪费
  2. 不同大小的块交错分配 → 堆中出现大量无法利用的"小空隙"（外部碎片）
  3. 释放时，如果 delete/update 涉及单词移除，碎片更严重
  4. 遍历时 cache miss 严重（块散布在堆各处）
```

### 3.2 StringPool 的解决思路

**把所有字符串打包进一块（或几块）连续内存中**，不单独 malloc。

```
StringPool 内部：
┌──────────────────────────────────────────────────────┐
│ code\0generation\0models\0translate\0natural\0...   │
│  ↑       ↑          ↑        ↑          ↑           │
│  池内偏移 0          偏移5     偏移16     偏移25       │
└──────────────────────────────────────────────────────┘

每个词只有 strlen+1 字节的存储，零额外元数据。
```

### 3.3 关键设计：指针稳定性

「池内指针」是整个系统的基石——词典的 key、语句中的词引用，全都指向池内。**如果池扩容导致 realloc 搬走了整块内存，所有指针全部失效。**

两种解决思路：

**方案 A：单块 + realloc（简单，但有风险）**

```
初始分配一个大块 → 满了就 realloc 2 倍大小
问题：realloc 可能（不确定）搬走数据，指针失效
适用：一次性加载所有数据，之后不再插入
```

**方案 B：链式块（推荐，适配增量场景）**

```
每块固定大小（如 64KB），满了就申请新块，挂在链表尾部

┌───────┐    ┌───────┐    ┌───────┐
│ Block0 │ → │ Block1 │ → │ Block2 │ → NULL
│ 64KB   │    │ 64KB   │    │ 64KB   │
└───────┘    └───────┘    └───────┘

优点：每个块独立分配，旧块地址永不改变 → 池内指针绝对稳定
缺点：块末尾可能有少量浪费（一个词不能跨块），最多浪费 max_word_len 字节/块
```

**我们选方案 B**，原因：
- 用户提到"增查需求"（增量入库），旧指针必须稳定
- 块末尾浪费微乎其微（最大浪费 ≈ 最长单词长度 ≈ 50 字节 / 64KB 块 = 0.08%）

### 3.4 驻留（Interning）——确保每个词只存一份

`intern(word, len)` 的工作流程：

```
intern("generation", 10):
  1. 查驻留表（一个小哈希表，key=字符串内容，value=池内指针）
     找到了 → 直接返回已有指针（不重复存储）
     没找到 → 继续步骤 2
  2. 检查当前块剩余空间
     够 → 追加到当前块尾部
     不够 → 分配新块，追加到新块
  3. 在驻留表中登记 "generation" → 新指针
  4. 返回池内指针
```

**驻留表与全局词典的关系**：

两个东西容易混淆：

| | 驻留表 (Intern Table) | 全局词典 (GlobalDict) |
|------|------|------|
| **用途** | 保证同一字符串在池中只有一份 | 分配词 → 整数编号的映射 |
| **key** | 字符串内容（临时传入的） | StringPool 指针 |
| **value** | StringPool 指针 | 整数编号（0, 1, 2, ...） |
| **何时用** | intern() 内部 | 建词典、查询时 |

实际上，可以**合并**：全局词典的 key 直接用 StringPool 指针，intern 后把指针插入词典分配编号。驻留表 = 全局词典的哈希表部分。（因为它们 key 都是词，value 不同而已。）

简化方案：用一个哈希表同时做两件事：key=词字符串，value= {pool_ptr, index} 结构体。但这会引入耦合。更清晰的做法是分开，驻留表只关心「存没存过」，词典只关心「编号是什么」。

## 四、函数解耦：如何切分代码

### 4.1 核心原则

一个函数只做一件事，一件完整的事。判断标准：
- 你能用一句话说清这个函数做什么吗？如果需要"和"、"以及"、"同时"，说明该拆了。
- 这个函数能否独立测试？不能的话，依赖太深。

### 4.2 模块划分

按数据流切分，沿着"数据从哪来、经过谁处理、到哪去"的线索：

```
document.txt
    │
    ▼
┌──────────┐
│ Tokenizer│  ← 负责：分句、分词、小写化、标点判断
│          │     产出：句子列表 → 每句一个 token 列表
└────┬─────┘
     │ 原始 token（可能含停用词）
     ▼
┌──────────┐
│ StopList │  ← 负责：判断一个词是不是停用词（仅此一个职责）
│          │     bsearch() 一行核心逻辑
└────┬─────┘
     │ 过滤后的有效词
     ▼
┌──────────┐     ┌────────────┐
│StringPool│◄───→│ GlobalDict │  ← 负责：
│          │     │            │     - intern 的写入端（词→池指针）
│          │     │            │     - 分配编号（池指针→整数索引）
│          │     │            │     - 反查（编号→词）
└────┬─────┘     └────┬───────┘
     │                │
     │  池指针        │  词索引（整数）
     ▼                ▼
┌──────────────────────────┐
│     SentenceStore         │  ← 负责：存句子元信息
│  - raw_text (char*)       │     - 提供遍历接口
│  - word_indices (int*)    │     - 提供按 sentence_id 取句
│  - struct_vec (float[7])  │
│  - l2_norm (float)        │
└────┬─────────────────────┘
     │
     ▼
┌──────────────┐
│ VectorBuilder│  ← 负责：从 token 列表算出 7 维结构向量原始值
│              │     从 word_indices 算出稀疏 TF 列表
└────┬─────────┘
     │
     ▼
┌──────────────┐
│  Normalizer  │  ← 负责：L2 归一化、min-max 归一化、min/max 收集
└────┬─────────┘
     │
     ▼
┌──────────────┐
│  Similarity  │  ← 负责：两个稀疏向量的余弦相似度（纯函数）
│              │     两个稠密 7 维向量的余弦相似度
└────┬─────────┘
     │
     ▼
┌──────────────┐
│ TopKSelector │  ← 负责：维护大小为 K 的小顶堆，提供 push/finalize
└────┬─────────┘
     │
     ▼
  Top-K 结果输出
```

### 4.3 哪些需要分开？哪些可以合并？

这是最容易纠结的地方。以下是具体的判断：

**必须分开的**（违反"一个函数一件事"就会乱）：
- `Tokenizer` ≠ `StopList`：分词是机械的字符判断，停用词是语义过滤，是两层逻辑
- `StringPool` ≠ `GlobalDict`：内存管理和编号分配是两个独立关注点。StringPool 不关心编号，GlobalDict 不关心内存怎么组织的
- `Similarity` ≠ `TopKSelector`：相似度计算是纯数学函数（给定两个向量 → 返回一个数），Top-K 是有状态的（维护一个堆），性质完全不同

**可以合并的**（分开了反而增加调用层数）：
- `VectorBuilder` 和 `Normalizer` 可以并入 `SentenceStore` 的构建流程中。因为只有在构建句子时才需要算向量 + 归一化，没有独立的复用场景。但如果后续 query 也要用同样的向量化逻辑，分开更好——**query 和 document 用同一套代码**。
- 驻留表（Intern Table）可以复用 `GlobalDict` 的哈希表基础设施，只是 value 类型不同。

**合并建议**：
- 把 `VectorBuilder` 保持独立（query 也要用），但它只做"计算原始值"，不做归一化
- `Normalizer` 独立：入库时收集 min/max，查询时用收集好的参数归一化
- 驻留表不单独实现，直接用 GlobalDict 的哈希函数 + 独立的 StringPool 内部小哈希表（内存布局不同，放一起反而别扭）

### 4.4 如何让代码量最小同时可读？

不是模块越少代码越少——**好的模块划分让每个文件变短，反而减少认知负担**。

每条具体的实践：

1. **每个 `.c` 文件不超过 200 行**（Tokenizer 可能超，这是正常的数据处理代码）
2. **每个 `.h` 文件暴露不超过 6 个函数**（多了说明模块职责不清）
3. **用 `static` 隐藏内部函数**：只在 `.c` 内部用的辅助函数加 `static`，`.h` 里不声明
4. **纯函数 vs 有状态模块**：
   - `is_punct()`, `to_lower()`, `cosine_sim()` → 纯函数，无状态，直接放在 `util.c` 里
   - `StringPool`, `GlobalDict`, `TopKSelector` → 有状态，各自一个 `.c/.h` 对
5. **常数集中管理**：`#define CHUNK_SIZE 65536`、`#define HASH_LOAD_FACTOR 0.7`、`#define STRUCT_DIM 7` 等统一放在 `config.h`

## 五、并行化机会

虽然 C 语言的并行需要 pthreads 或 OpenMP（对课程项目不一定需要），但理解"哪些任务可以并行"有助于设计更清晰的数据流。即使不用多线程，**理解依赖关系也能帮我们排出一个高效的串行顺序**。

### 5.1 入库阶段的依赖分析

```
读文档 → 分句 → 分词 → 去停用词 → intern → 词典插入 → 算向量 → 存句子
                                    │                    │
                                    └─ 依赖顺序 ────────┘
```

**句子之间是完全独立的**——句子 A 的分词不依赖句子 B。这意味着：

```
如果并行：
  Thread 0: 处理句子 0~999    → 各自 tokenize → 各自的词分别 intern
  Thread 1: 处理句子 1000~1999
  ...
  冲突点：intern() 和 GlobalDict 的插入需要同步（因为要分配唯一编号）
```

**但同步开销可能大于收益**。更实际的做法是「两遍扫描」：

- **第一遍**：只做词典构建。扫描所有句子，只 intern + 词典插入，不存句子细节。
- **第二遍**：词典已经固定（N_dict 不变，哈希表不会 rehash）。扫描所有句子，分词 → 查词典（纯读！无写冲突）→ 构建向量 → 存句子。

**第二遍天然可以并行**：因为词典是只读的，每个句子独立处理，零同步。如果数据量大，这里是最值得并行化的地方。

### 5.2 查询阶段的并行化

查询阶段计算 query 与每条句子的相似度——**句子之间完全独立**：

```
for sentence in sentences:       ← 这个循环可以并行！
    score = similarity(query, sentence)
    heap.push(score)
```

但 TopKSelector 的 `push` 是写入操作，需要同步。简单的做法：
- 每个线程维护自己的局部小顶堆
- 最后合并所有局部堆 → 全局 Top-K

**如果不用多线程**，串行遍历已经是 O(N log K)，对于中等规模（< 10 万句）足够了。

### 5.3 预计算的策略

有些计算可以提前做，用空间换查询时间：

| 预计算项 | 成本 | 收益 |
|------|------|------|
| 每条句子的 L2 范数 | O(句长)，入库时算一次 | 查询时余弦相似度直接用，省去重复开方 |
| 每条句子的归一化结构向量 | O(7)，入库时算 | 查询时直接取用（但如果增量影响 min/max，需要更新） |
| 每句稀疏 TF 按 index 排序 | O(tokens log tokens)，入库时排一次 | 查询时双指针归并 |

### 5.4 流水线视角

把入库看作一个流水线，而不是一个巨大的单步操作：

```
分句器 ──→ 分词器 ──→ 词典构建器 ──→ 向量构建器 ──→ 存储
  │           │            │               │
  └── 每完成一句就可以传给下一级，不需要等所有句子都分完
```

但实际上，"词典构建"需要看到所有词才能确定 N_dict，所以不能完全流水线化。两遍扫描是合理的折中。

## 六、完整流程 + 小数据样本走读

现在把所有东西串起来，用题目样例 trace 一遍完整流程，看看每个数据结构在什么时刻是什么状态。

### 6.1 样例输入

```
document.txt（10 句，关于 code generation 模型）
stopList.txt（891 个停用词）

α = 0.6
K = 3
```

### 6.2 入库第一遍：构建 StringPool + GlobalDict

**Step 1 — 分句**：扫描 document.txt，遇到 `.` `?` `!` `\n` 切分 → 10 个句子字符串。

**Step 2 — 逐句分词、intern、词典插入**：

以第一句为例：
```
原始: "Code generation models can translate natural language to source code."

分词（按空白+标点切，保留 ' 连词）+ 小写:
  → "code" | "generation" | "models" | "can" | "translate" | "natural"
    | "language" | "to" | "source" | "code"

去停用词（二分查找判断每个 token）:
  "can"  → 在停用词表中 ✓ → 丢弃
  "to"   → 在停用词表中 ✓ → 丢弃
  其余   → 不在 ✗ → 保留

有效词: code, generation, models, translate, natural, language, source, code
```

每个有效词依次 intern：
```
intern("code")        → StringPool 空，追加 → ptr=0x1000, 驻留登记
GlobalDict.add(0x1000) → 哈希表 [hash("code")] 空 → 插入, 分配编号 0
                          word_by_index[0] = 0x1000

intern("generation")  → 追加 → ptr=0x1005, 驻留登记
GlobalDict.add(0x1005) → 分配编号 1
                          word_by_index[1] = 0x1005

intern("models")      → 追加 → ptr=0x1010
GlobalDict.add(0x1010) → 分配编号 2

...（以此类推）

intern("code")        → 驻留表命中！返回 0x1000（已有指针）
GlobalDict.add(0x1000) → 哈希表查找命中 → 返回编号 0（不新增）
```

**第一遍结束时的状态**（处理完 10 句）：

```
StringPool（链式块，64KB 每块）:
┌──────────────────────────────────────────────────┐
│ code\0generation\0models\0translate\0natural\0... │  ← 43 个不同词
│ language\0source\0based\0...evaluation\0benchmarks\0│     连续存放
└──────────────────────────────────────────────────┘

GlobalDict 哈希表（size=64，负载 43/64=0.67）:
  [12]: key=0x1000 → val=0   (code)
  [27]: key=0x1005 → val=1   (generation)
  [ 5]: key=0x1010 → val=2   (models)
  ...（线性探查解决冲突的槽位省略）

word_by_index[0..42]:
  [0]="code", [1]="generation", [2]="models", [3]="translate",
  [4]="natural", [5]="language", [6]="source", [7]="based",
  [8]="gpt", [9]="evaluating", [10]="robustness", [11]="reliability",
  ... [41]="evaluation", [42]="benchmarks"
  N_dict = 43
```

### 6.3 入库第二遍：构建 SentenceStore + 向量

再次扫描所有句子（因为此时只需查词典，不写词典，可以并行）。以第一句为例：

```
第一句有效词: code, generation, models, translate, natural, language, source, code

查 GlobalDict（纯读操作，O(1) 每次）:
  "code"       → 0
  "generation" → 1
  "models"     → 2
  "translate"  → 3
  "natural"    → 4
  "language"   → 5
  "source"     → 6
  "code"       → 0（重复，TF[0] += 1）

word_indices = [0, 0, 1, 2, 3, 4, 5, 6]
排序后 = [(0,2), (1,1), (2,1), (3,1), (4,1), (5,1), (6,1)]
  // code 出现 2 次 → TF=2，其余 1 次

L2 范数 = sqrt(2² + 1²+1²+1²+1²+1²+1²) = sqrt(10) ≈ 3.1623

结构向量原始值（计算过程见题目 stem）:
  [平均词长, 词长方差, 有效词数, 平均元音比例, 标点密度, 大写密度, 数字密度]
```

10 句全部处理完后，收集所有结构向量各维度的 min/max，用于归一化。

### 6.4 查询阶段

```
Query 原始: "How can we evaluate or test the robustness of code generation models?"

分词 + 小写:
  how | can | we | evaluate | or | test | the | robustness | of | code | generation | models | ?

去停用词（how, can, we, or, the, of 都在停用词表中）:
  → evaluate | test | robustness | code | generation | models

查 GlobalDict（只查不增）:
  "evaluate"   → 哈希查找 → NOT_FOUND（表中是 "evaluating" #9 和 "evaluation" #41，没有 "evaluate"）
                  → 跳过，不加入语义向量
  "test"       → 19 ✓
  "robustness" → 10 ✓
  "code"       → 0  ✓
  "generation" → 1  ✓
  "models"     → 2  ✓

Query 语义向量（稀疏 TF，每个词 1 次）:
  [(0,1), (1,1), (2,1), (10,1), (19,1)]
  L2 范数 = sqrt(5)
  归一化后各分量 = 1/sqrt(5) ≈ 0.447214  ← 与题目样例一致
```

### 6.5 相似度计算（以句子 0 为例）

**语义相似度 — 双指针归并**：

```
Query 稀疏列表:  [(0,1), (1,1), (2,1), (10,1), (19,1)]    (5 个元素)
句子0 稀疏列表:  [(0,2), (1,1), (2,1), (3,1), (4,1), (5,1), (6,1)]  (7 个元素)

归并过程:
  q_ptr=0, s_ptr=0: q[0]==s[0]==0 → 点积 += 1×2 = 2, 双指针前移
  q_ptr=1, s_ptr=1: q[1]==s[1]==1 → 点积 += 1×1 = 1, 双指针前移
  q_ptr=2, s_ptr=2: q[2]==s[2]==2 → 点积 += 1×1 = 1, 双指针前移
  q_ptr=3, s_ptr=3: q[10] > s[3] → s_ptr++（句子有词 query 没有）
  ...以此类推

点积 = 2+1+1 = 4

cos = 点积 / (|q| × |s|) = 4 / (1 × sqrt(10))    // |q|=1（已归一化）
    = 4 / 3.1623 = 1.2649... 
    
等等，不对。让我重新算。
点积应该用归一化后的值：
q 归一化: (0, 1/sqrt(5)), (1, 1/sqrt(5)), (2, 1/sqrt(5)), (10, 1/sqrt(5)), (19, 1/sqrt(5))
s 值（未归一化）: (0,2), (1,1), (2,1), (3,1), (4,1), (5,1), (6,1)

点积 = (1/sqrt(5))×2 + (1/sqrt(5))×1 + (1/sqrt(5))×1 = 4/sqrt(5) ≈ 1.78885

cos = 4/sqrt(5) / (1 × sqrt(10)) = 4/sqrt(50) = 4/7.071 = 0.565685 ✓
```

与题目样例 `语义: 0.565685` 吻合。

**混合相似度**：
```
hybrid = 0.6 × 0.565685 + 0.4 × 0.965713 = 0.725697
```

### 6.6 Top-K 选择

遍历 10 句，用小顶堆（K=3）维护最高分：

```
初始: 堆空
句子0 score=0.7257 → 插入 [{0.7257, sid=0}]
句子1 score=0.xxxx → 插入 [{0.xxxx, sid=1}, {0.7257, sid=0}]
句子2 score=0.7539 → 插入，堆满 [{0.7257,sid=0}, {0.xxxx,sid=1}, {0.7539,sid=2}]
                      堆顶 = 0.xxxx（最小值）
句子3 score < 堆顶 → 跳过
...
句子4 score=0.6139 → 检查：0.6139 < 堆顶？若堆顶是最小值 0.7257 → 跳过
...

最终堆: [{0.6139,4}, {0.7257,0}, {0.7539,2}]
弹出反转: [句子2, 句子0, 句子4]
```

输出：

## 七、大规模数据下的优化路径

### 7.1 瓶颈在哪

| 阶段 | 复杂度 | 1 万句 | 100 万句 |
|------|------|:---:|:---:|
| 入库-分句分词 | O(total_chars) | ~1ms | ~100ms |
| 入库-词典构建 | O(N_words × 1) 均摊 | ~10ms | ~1s |
| **查询-遍历所有句子** | **O(N × avg_q_words)** | **~1ms** | **~100ms** |
| 查询-TopK | O(N log K) | ~0.1ms | ~10ms |

查询的遍历是瓶颈，因为朴素的相似度计算要对每条语句都做一遍。

### 7.2 倒排索引（候选召回 + 精排）

倒排索引的思想：对于语义子向量的点积，**只有 query 词和句子词的交集才有贡献**。如果 query 有 5 个词，那么只有包含这 5 个词中至少一个的句子才需要参与计算。

```
朴素: for each sentence: 点积    → O(N_sentences × avg_q_words)
倒排: for each query_word:
        取出 posting_list(word)    → 所有包含该词的句子
        对每个句子累加得分
      → O(sum |posting_list|) ≈ O(N_sentences × P)，P 是平均命中率 << 1
```

两阶段策略：
1. **召回**：用倒排索引 + 语义相似度筛出 Top-M（M ≈ 10K）
2. **精排**：对召回候选计算完整混合相似度（含结构分量），输出 Top-K

### 7.3 StringPool 的大规模表现

- 100 万不同单词 × 平均 8 字符 = 8 MB 纯字符串
- 链式块（64KB/块）→ 约 128 个块 → 极小的管理开销
- 对比每词独立 malloc：100 万次 × ~16 字节元数据 ≈ 16 MB 额外浪费
- 节省约 50% 内存

### 7.4 是否需要一开始就做倒排索引？

**不需要。** 先用朴素遍历把整个流程跑通。原因：
- 朴素遍历代码量小，容易调试
- 对课程级别的数据量（几千句以内），朴素遍历已经够快了（< 10ms）
- 倒排索引可以后续加上——只要 SentenceStore 接口不变，改 Similarity 内部实现即可

## 八、实现顺序建议

按这个顺序开发，每步都能单独测试：

```
Step 1: Tokenizer
  输入: 一个字符串
  输出: 分句后的句子数组 + 每句的 token 列表
  测试: 打印分句结果和分词结果，肉眼验证

Step 2: StopList + StringPool
  输入: stopList.txt
  输出: 能判断 is_stopword()，能用 intern() 存储字符串
  测试: 对几个词测二分查找，打印池内容

Step 3: GlobalDict
  输入: 经过 Step 1-2 处理过的 token 流
  输出: 词→编号映射，word_by_index[] 反查
  测试: 第一遍扫描后打印 N_dict 和词典内容，与题目样例对照（43 个词）

Step 4: SentenceStore + VectorBuilder + Normalizer
  输入: 第二遍扫描的 token 流
  输出: 所有句子的稀疏向量 + 结构向量 + L2 范数
  测试: 打印某句的向量，与题目样例对照

Step 5: Similarity + TopKSelector
  输入: query 文本 + α + K
  输出: Top-K 句子文本
  测试: 用题目样例，检查输出是否完全匹配
```

## 九、设计决策速查表

| 决策点 | 选择 | 核心理由 |
|--------|------|------|
| 字符串管理 | StringPool + 链式块 | 避免碎片，指针稳定，支持增量 |
| 停用词查找 | 有序数组 + 二分 | 数据天然有序，零预处理，`bsearch()` 一行搞定 |
| 词典查找 | 开放寻址哈希（线性探查） | 无删除，cache 友好，负载可控 |
| 冲突解决 | 线性探查 + 低负载因子 0.6 | 实现简单，可后升级 Robin Hood |
| 哈希函数 | 预计算 + 缓存 hash 值 | 每个词只算一次，查找时先比 hash 再 strcmp |
| 语义向量 | 稀疏 `(index, tf)` 对 | 每句 5-30 个非零 vs 数万维，稀疏存储节省两个数量级 |
| 结构向量 | 存原始值 + 查询时实时归一化 | 支持增量不破坏已有数据 |
| Top-K | 小顶堆 (size=K) | O(N log K)，K 小到几乎可忽略 |
| 查询遍历 | 朴素遍历（先跑通）/ 倒排索引（后续加） | 分阶段引入复杂度 |
| 模块封装 | 每模块一个 .c/.h，不透明指针 | 改内部实现不影响调用者 |
